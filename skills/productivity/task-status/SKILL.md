# task-status

用户在项目会话中途调用 `$task-status`，需要一份既方便自己判断状态、又能直接向同事或上级转述的简明摘要。一次调用完成会话输出和当天日报 log 记录；不要拆成自用版、汇报版，也不要把摘要写成正式日报。

## 确定范围与事实

1. 以**发起调用的当前会话、当前任务和项目**为范围。先回顾本会话中的目标、已确认结果、正在进行的事、用户的最新决定与未解决问题。不同会话不能沿用彼此的状态。
2. 找到当前项目主文件夹，只读查看直接相关的最新记录，例如项目进度文件、任务文档、适用的 `AGENTS.md`，以及确有必要时的本地 Git 状态。优先核对可能改变结论的记录；不为一次速览遍历整个项目或读取无关资料。项目路径或任务边界不清时，先从会话和工作目录判断；仍无法确定时，向用户确认，且在确认前不要把别的项目内容写进摘要或日报。
3. 以当前可核实的事实和最新明确决定为准。区分计划、已做动作、验证结果与最终完成；不把计划或旧记录推断为已完成，不把测试、提交、推送、部署、验收混为一谈。有冲突时核对较新的原始记录；仍有冲突就写明待确认。只读取材，不修改项目文件、分支或外部系统。

## 形成一份两用摘要

只输出 **「当前进度」和「当前卡点」** 两部分。每部分选最重要的 1–3 个一级条目；没有可确认进度时用一句话说明证据不足，没有已确认卡点时写“目前没有已确认的阻碍”。每个一级条目优先写成**一句可直接转述的话**：进度交代成果或当前状态，卡点交代问题、影响和所需确认或动作。按任务或问题归类，不强制套用“已完成／正在做／下一步”，也不为凑数添加条目。

- 每个一级条目最多 3 个二级条目；只有确实影响理解时才细分，每个二级最多 3 个三级条目。最多三级；无必要就只写一级。
- 语言通俗、客观、简洁。专业术语只在影响判断时使用；同一事实不要在进度和卡点中重复叙述。
- 根据证据来源、时效和是否经过验证，在内部评估每个条目的置信度。低于 30% 时，在**对应条目末尾**加 `（置信度低，不确定）`；其他条目不显示分数或标签。不能因有这个标签就把无依据的猜测写成事实；没有依据时直说“无法确认”。
- 必要的细节、依据、子问题可放在二级或三级条目，不改变一级条目的简明表达。涉及个人凭据、内部密钥等敏感值时不写入摘要或 log。

## 双线交付

1. 按当前会话所在时区取得调用当天日期和时间。日报目录优先采用用户本次指定位置，其次采用当前项目已明确配置的位置；两者都没有时使用当前项目根目录下的 `日报/daily-report/`，目标文件为 `{YYYY-MM-DD}-log.md`。解析为绝对路径后再写入；不得沿用其他设备的历史目录。
2. 先读取当天 log（若存在），保留已有内容。按 `daily-report log` 的过程记录习惯，追加一个带 `HH:MM` 的「进度记录」快照，写入**与会话展示相同的「当前进度／当前卡点」摘要**；不要覆盖、改写既有记录，也不要把同一调用重复追加两次。文件不存在时创建并写入 `# 日报过程记录 — {YYYY-MM-DD}` 标题。
3. 在当前会话展示同一份摘要，并给出 log 文件链接。若文件写入失败，仍展示摘要，明确说明未能记录及原因；不要声称已写入。除这两处输出外，不自动生成 plan、final、周报，也不发送给其他人。

调用 `$task-status` 即授权追加这次状态快照到当天 log；不需要在已经明确的项目和目录上重复询问。若用户在调用时指定只查看或暂不记录，则遵从其本次要求。
